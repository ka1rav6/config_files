# Terminal Renderer Engine

## Overview

Imagine OpenGL -> but for the terminal. This is not a TUI library, nor is it limited to TUI apps. It is the foundation for building entire interactive worlds inside a terminal emulator.

### Applications

- **Terminal Games** -> Push gaming to a whole new level. Imagine SSH-ing into a server and playing a Minecraft clone rendered entirely in the terminal.
- **The "From Scratch" Feeling** -> Recreate the magic of building your first OpenGL project, but this time in the terminal.
- **Physics Simulations** -> Build and share physics simulations that anyone can run with just a terminal.
- **Enhanced Text Editors** -> Give editors like Vim a new identity with animated loading screens, custom rendering, and visual effects.
- **Retro Game Development** -> A perfect tool for retro-game creators and enthusiasts.
- **Superior Monitoring Tools** -> Think `btop`, but more powerful and easier to build.
- **Tutorials and Graphics** -> Create actual videos and graphics inside terminals for tutorials and demonstrations.
- **Terminal Browser / HTML-CSS Renderer** -> Build a fully functional browser that renders HTML and CSS directly in the terminal.

### The Constraint

Standard graphics rely on millions of pixels. A terminal, by contrast, is a character grid -> typically around 4096 characters (80×48). Can we still build rich visuals?

**Yes.**

Unicode characters make this possible. Block elements, braille patterns, and shade characters allow us to subdivide each terminal cell into a fine-grained pixel grid. Resources like [Compart's Unicode Search](https://www.compart.com/en/unicode/search?q=block#characters) demonstrate the breadth of characters available.

#### Unicode Character Examples

Here are key Unicode character ranges that enable terminal rendering:

| Range | Name | Count | Pixel Resolution per Cell | Use Case |
|---|---|---|---|---|
| `U+2800`–`U+28FF` | Braille Patterns | 256 | 2×4 | High-density pixel art, detailed graphics |
| `U+2580`–`U+259F` | Block Elements | 32 | 2×2 | Gradients, shading, simple shapes |
| `U+2591`–`U+2593` | Shade Characters | 3 | 1×1 | Simple brightness levels |
| `U+2500`–`U+257F` | Box Drawing | 128 | -> | Borders, UI frames, wireframes |
| `U+1FB00`–`U+1FB3B` | Block Sextants | 60 | 3×2 | Finer pixel density than block elements |

Using these, a single terminal cell can represent:

- **8 pixels** (braille: 2×4 grid)
- **4 pixels** (block elements: 2×2 grid)
- **6 pixels** (sextants: 3×2 grid)

Yes, we will have to work creatively around character limitations, but the result will be remarkable.

### Phase 1 -> 2D Terminal Graphics

This phase establishes the core rendering system. Scalability is the top priority.

### Phase 2 -> 3D Rendering Pipeline

This phase introduces a full graphics pipeline for 3D content.

1. **Math library** -> Vectors, matrices, matrix multiplication, projection matrices, view transforms.
2. **3D model rendering pipeline:**
   ```
   3D Model → Vertex Processing → Mathematical Transformations
   → Projection onto Terminal Grid → Character Shading → Frame Buffer
   ```
3. **Camera and interaction** -> Views, camera controls, and input-driven navigation.
4. **Lighting** -> Approximate lighting using braille characters and block elements with varying fill densities.
5. **Software rasterizer** -> A fully functional, custom-built rasterizer.

#### Unicode Storage Strategy

A common question: how do you work with hundreds of Unicode characters without embedding them all as string literals?

**The answer: compute code points at runtime.**

Unicode characters are just integers. The braille block `U+2800`–`U+28FF` encodes an 8-dot pattern (2 columns × 4 rows). Given a 2×4 pixel block, you compute the code point directly:

```c
// Braille encoding: each dot maps to a bit in the code point
// Layout:
//   dot1  dot4
//   dot2  dot5
//   dot3  dot6
//   dot7  dot8

uint32_t encode_braille(uint8_t pixels[2][4]) {
    uint32_t codepoint = 0x2800;
    codepoint |= (pixels[0][0] ? 1 : 0) << 0;  // dot1
    codepoint |= (pixels[0][1] ? 1 : 0) << 1;  // dot2
    codepoint |= (pixels[0][2] ? 1 : 0) << 2;  // dot3
    codepoint |= (pixels[0][3] ? 1 : 0) << 3;  // dot7
    codepoint |= (pixels[1][0] ? 1 : 0) << 4;  // dot4
    codepoint |= (pixels[1][1] ? 1 : 0) << 5;  // dot5
    codepoint |= (pixels[1][2] ? 1 : 0) << 6;  // dot6
    codepoint |= (pixels[1][3] ? 1 : 0) << 7;  // dot8
    return codepoint;
}
```

For block elements, the approach is similar -> map pixel regions to the corresponding code point. For shaded characters, you threshold a luminance value and pick `U+2591` (light), `U+2592` (medium), or `U+2593` (dark).

In languages like Zig, compile-time computation (`comptime`) can generate lookup tables automatically, so the mapping is resolved before the program even runs -> zero runtime cost.

## Tech Stack

### Option 1: C++

| Pros | Cons |
|---|---|
| Single language | Lower community adoption |
| Familiar to most developers | C++ complexity can escalate quickly |
| Strong compiler optimizations | Header files add friction |
| OOP support for clean architecture | |
| Namespace support | |
| Strong job market relevance | |

### Option 2: Zig + C

| Pros | Cons |
|---|---|
| Strong open-source community and committee | API is still evolving |
| Clean code with excellent C interop | Not widely adopted in job market |
| Built-in optimizations | No OOP |
| `@Vector` with native SIMD support | No namespaces |

**Proposed split:**

- **Zig** -> High-level API, main application logic, SIMD optimizations via `@Vector`, parser, and utility functions.
- **C** -> Low-level terminal I/O (termios), system-level optimizations, and platform-specific handling.
